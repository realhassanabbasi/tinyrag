How it works

The whole pipeline — chunking, TF-IDF, retrieval, answering — is written by hand in pure Python. No sklearn, no numpy, no LLM.

01

Chunk

Documents split into a sliding window of 400 words with 80-word overlap.

→
02

Vectorize

TF-IDF from scratch, L2-normalized, English stopwords removed.

→
03

Retrieve

Cosine similarity ranks the chunks; the top-k go to the answerer.

→
04

Answer

Best sentence by IDF-weighted term overlap, quoted with its source.

What it can do

Eleven commands, one loop: index → ask → inspect → guard → serve.

index

Build a persistent JSON index from a folder of .txt / .md files. Build once, ask anytime.

ask

Extractive answers with a citation — document, chunk, confidence. --sources N shows the ranked evidence behind it.

search

List the chunks that mention a word, with scores and excerpts — the same retriever ask uses, so they always agree.

stats

Documents, chunks, vocabulary, per-document counts, most common terms — read straight from the saved index.

refresh

Re-index only added or edited files; drop deleted ones. A no-change refresh says so.

check

Re-answer a saved question set after a refresh and flag answers that moved or vanished. CI-ready with --fail-on-change.

ask-batch

Run a whole question set through the ask pipeline and print the answers with sources, or write them as a Markdown FAQ with -o.

compare

Answer the same question set on an old index and a new one and report what changed: same, changed, moved, newly answered, lost, or still unanswered.

merge

Combine two indexes into one searchable index with IDF rebuilt over the merged corpus; exact duplicates kept once, conflicts keep the first index’s version.

diff

Show what content changed between two index files, doc by doc — run it before a merge, since a changed doc is exactly the doc merge resolves first-wins.

serve

Ask in the browser — a tiny local web UI on localhost with the same quoted answers, plus JSON endpoints for scripts; --index-dir serves every index with a picker.

Ask in the browser

Every command so far is terminal-only, and this page is static — it can show the loop but it cannot answer your questions. serve closes that gap: one command starts a tiny web UI over the index you already built, on localhost only. The page is one built-in string — no files are served from disk — and every question runs through the exact ask pipeline, so a browser answer can never disagree with the terminal answer.

$ tinyrag serve --index-dir indexes
serving 2 indexes (course, plants) at http://127.0.0.1:8000 — Ctrl+C to stop
skipped 1 file(s) that are not indexes: stray.json
$ curl http://127.0.0.1:8000/health
{"ok": true, "indexes": [{"name": "course", "docs": 3, "chunks": 3}, {"name": "plants", "docs": 1, "chunks": 1}], "version": "1.11.0"}
$ curl -X POST http://127.0.0.1:8000/ask \
  -H 'Content-Type: application/json' \
  -d '{"question": "what is photosynthesis", "index": "plants"}'
{"question": "what is photosynthesis", "answer": "Photosynthesis Photosynthesis is the process by which green plants convert sunlight, water and carbon dioxide into oxygen and glucose.", "doc": "plants.txt", "chunk_id": 0, "confidence": 0.46, "sources": [{"rank": 1, "doc": "plants.txt", "chunk_id": 0, "score": 0.46, "excerpt": "Photosynthesis Photosynthesis is the process by which green plants convert sunlight, water and carbon dioxide into oxygen and glucose. Chlorophyll in the leaves captures light energy."}], "index": "plants"}

One server for every index you have: the page gets an index picker, and the answer payload names its index, so a script answer is never ambiguous about its source. The index name is the file stem (course.json → course). Files that are not valid indexes are skipped and named — a stray file never stops the server. Ask without an "index" when several are loaded and the server refuses instead of guessing:

{"error": "pick an index", "indexes": ["course", "plants"]}

All serve output above is real, captured from the installed package.

Honest limitations

  • English-only tokenizer — other languages won’t tokenize.
  • Keyword matching, not semantics — “car” won’t match “automobile”.
  • Small-scale by design — the whole index lives in memory as JSON; fine for notes and docs, not millions of pages.
